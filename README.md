# Pi Extensions

This repository contains small, independently removable Pi extensions. It exports thirteen maintained extensions: `multi-skill-mentions`, `fast-gpt`, `agents`, `agents-ui`, `status-footer`, `work-timing`, `tasklist`, `notices`, `tasks-ui`, `jobs-ui`, `agent-bark`, `async-bash`, and `cache-keepalive`, while preserving Pi's authoritative host agent loop. `agents-ui` is default-loaded as a TUI-only read-only observer.

## Multi-skill Mentions

Type `$` in the TUI to search loaded skills. A leading selection prefix accepts repeated or mixed `$skill-name` and `/skill:name` tokens in either order; dollar mentions elsewhere still select loaded Skills and preserve the user's prose. Selections deduplicate in encounter order. Multiple selections use one native-compatible card showing every selected name, with each actual path, reference base and body preserved. Unknown names, escaped mentions such as `\$skill-name`, ordinary shell variables and non-leading slash prose remain literal. A read failure restores the original input and discards the partial selection.

`/skill-mentions` shows a short usage reminder and the number of currently loaded skills. Pi's command registry supplies the extension's authoritative available skill names and source paths.

## Fast GPT

`/fast-gpt` toggles a branch-local request profile between priority and explicit default service tiers. The extension leaves requests untouched until the first command. In priority mode it adds top-level `service_tier: priority` to correlated official OpenAI and OpenAI-Codex Responses requests; the next toggle sends top-level `service_tier: default`. Unsupported provider, API, or model correlations remain unchanged.

This is only a request payload profile. Its keyed status is a lightning mark confirming that priority was requested; provider service requires separate evidence. The final response body's `service_tier` remains unavailable through Pi's extension API, and the OpenAI-Codex endpoint has an additional response-accounting caveat. Pi and provider-side billing remain authoritative for usage and cost. Model aliases, provider overrides, pricing parsers, live calls, and workflow behavior remain outside the extension's scope. See [`docs/architecture/fast-gpt.md`](docs/architecture/fast-gpt.md) for state, correlation, response observability, ownership, and removal contracts.

## Agents

The source collaboration contract is v4, using [Git worktrees and session-scoped asynchronous execution](docs/architecture/agent-execution.md). One business task can read multiple locations and write multiple repositories through one `access` collection of read/write grants with absolute scalar or nonempty-list `scope` selections. Write includes read; unsupported managed-write backends fail honestly. Admission captures dirty/staged/untracked Git input and preserves the parent index. TUI/RPC create and continue return accepted receipts while preparation and one native child proceed under the owning session. A receipt records accepted submission; completion requires execution evidence.

`agent` supports explicit `create`, `continue`, `inspect`, `join`, `cancel`, `refresh`, `apply`, and `close` for explorer, reviewer, and worker tasks. One-shot hosts default to foreground; TUI/RPC callers can request `mode: "foreground"` or explicitly join a dependency. Independent submissions share capacity and locks. Ordinary delegation is a flat create batch; optional hard predecessor edges support approved implementation order with no intervening parent decision. Dependency edges pass predecessor reports; candidate files require explicit parent `apply`. File-dependent successors require explicit parent `apply` between dispatches. Assignments run in separate agent contexts and can execute in parallel within configured capacity. Explorer, reviewer and worker roles describe investigation, evaluation and implementation; grants determine actual permissions. The caller chooses task decomposition, delegation appetite and verification strategy through user direction or applicable method guidance; any Skills collection is optional. Results are candidates with actual evidence and uncertainty; the parent retains integration, continuation, candidate application, acceptance and the final response.

Role labels (`explorer`, `reviewer`, `worker`) express purpose and routing preferences; grants and ownership determine permissions. Eligible configured native, extension and MCP tools remain available; explicit read-only intent, access grants and real ownership still bind. Known typed operations enforce those bounds; trusted shell and third-party code operate outside an OS sandbox.

Each managed episode uses retained native history, with a prepared workspace and private index for every writable Git root. One native child can exercise real dependencies between those roots; source-to-prepared mappings keep same-relative-name files distinct. Dependencies and ignored environments remain outside copying and certification. Actual authorized additions, deletions, renames, mode changes, binary files and contained symlinks form one immutable candidate bundle. Continue keeps its input; only explicit idle refresh changes it.

Apply preflights the complete bundle under destination-resource coordination, then integrates roots individually; cross-repository atomicity is unavailable. Already-applied roots stay recorded when a sibling conflicts or has unknown progress; retries reconcile that evidence before mutation and preserve parent staging. Report completion, execution, candidate application, parent acceptance, retention and resource release remain distinct. Close may retain resources; a closed-retained record can later be discarded. Discard retries exact remaining owned refs, worktrees and scratch while retaining registry/native evidence. Historical envelopes are shallowly excluded before decoding, migration or use for current action semantics. See [execution and recovery](docs/architecture/agent-execution.md).

Foreground tool progress uses `Agents {running}/{total} running, {finished} finished · {turns} turns · {clock}`; asynchronous progress uses the observer after the submission callback settles. Persisted terminal events own execution accounting and coalesced current-owner wake. Default-loaded `agents-ui` is a read-only observer. Bare `/agents-ui` toggles the above-editor section. Its header expands or collapses bounded inline agent rows independently of Tasks and Jobs. It appears when the session has published agent state, unless that command has hidden it. `/agents-ui list` and `Ctrl+Alt+F` open the session-wide floating panel. Fresh running agents stay pinned above Enter-expanded retained history; PageUp/PageDown navigate history pages and arrows reveal wrapped rows. Continuing a handle preserves its identity while episodes are counted separately. Closed and same-session historical-branch records remain visible while mutation authority retains its existing bounds. Inline agent rows include episode/state/outcome, route and recorded usage in footer-style `↑ ↓ R W CH $` units, with `CH` tied to the latest recorded assistant prompt; the session footer provides the cumulative ratio. Core-owned retained queries provide page-independent recorded usage, explicitly labeling incomplete or unavailable metrics; bounded observer snapshots supply live evidence; retained queries provide session totals. The panel shares the transparent rounded frame of the Tasks and Jobs lists, adapts to terminal dimensions and keeps its `×` close mark. The old below-editor live-row widget remains unmounted, and custom completion entries stay off. See [Agents UI](docs/architecture/agents-ui.md). `status-footer` and `work-timing` remain independent. Managed results distinguish request and episode outcomes, stored state, report completeness, and apply facts. A failure the extension cannot type keeps the `managed_operation_failed` code plus a bounded, path-free `detail` reason (errno code or error name) to make the failure distinguishable. Acceptance remains a parent judgment; runtime result fields and warnings provide evidence for that judgment.

Loading Agents registers only `agent`, `/agents` status and observer hooks. Static operation guidance uses Pi's native prompt assembly; Agent index and input/compaction refresh messages remain absent. Bare `inspect` discovers supported retained Agents and actionable result references after input, resume or compaction. Child and workspace preparation begins only after the applicable operation is called. Trusted-project admission validates the normalized absolute grants and physical owners before preparation; authority comes from validated grants and physical owners; cwd, a role, an environment variable and tool availability remain separate inputs. Prepared mappings cover writable Git roots and associated reads, while independent read roots remain read-only. Readable task labels are bounded nonblank text, unique only within one batch; dependencies use those local labels. The host generates persistent handles and derives replay identity from the stable tool-call boundary. A repeated accepted call replays, while an independent call may reuse a label for a distinct Agent. Rejected admission releases its reservation. Opaque handles/candidate IDs and exact episodes remain separate, copied unchanged for guarded operations. Native session IDs and Git OIDs remain opaque external values.

The repository ships its route baseline at [`config/agent-routes.json`](config/agent-routes.json). It prefers explorer Luna medium, worker Terra high, and reviewer Sol high, with explicit peer fallback order, global concurrency 10, per-role defaults `4/4/2`, thinking-profile mappings. Tool guidance describes capability and operation; the caller chooses delegation preferences. Model names remain opaque configuration; peer-family ranking remains outside extension code.

The user override is `agent-routes.json` under Pi's agent directory; it is the only user route file, read independently of the package baseline. Invalid or unsafe input fails visibly; fallback is unavailable. `/agents` and configuration source metadata report the selected filename. The extension leaves the file unchanged, and its absence applies the package baseline. A strict overlay may replace role candidates, add execution-profile candidate lists, override thinking-profile entries, or replace global and per-role concurrency with positive safe integers. When role capacities sum above the global value, the scheduler accepts the configuration and uses the global value as the launch limit. Package and user files are read-only persistent defaults: the extension leaves their creation, editing, and deletion to their owners. A legacy `reasoningProfiles` key is rejected as invalid route configuration and remains unapplied and unchanged; rename it to `thinkingProfiles`. The retired `guidance` setting is also rejected by the closed config schema; remove it explicitly before using this version, expressing any desired delegation preference through user instructions or an applicable method. The extension leaves personal files unchanged for both changes.

Tasks may provide optional provider-neutral `executionProfile` and `thinkingProfile` values; missing or unmapped values visibly use the role default. Model-visible results and TUI summaries show the actual provider/model/thinking, requested profiles, whether each applied, and any profile fallback. The actual provider/model/thinking in the result identifies the worker selection; the requested `deep` profile and parent model are separate facts. An explicitly user-selected `model` or Pi `thinking` level is ephemeral, resolves against Pi's registry, and overrides defaults; an invalid exact selection fails visibly with no fallback. Plans, Skills and Codex agent files remain outside the extension's inputs; the parent model and provider settings remain user-owned and unchanged by the extension. JSON owns persistent routing defaults; access grants own permissions.

Current readers distinguish excluded, invalid and unavailable evidence. Current-version records that still carry `reasoningProfile` request or receipt fields are excluded the same way: they remain unmigrated, unchanged, and excluded from profile-less successes. See [Agents](docs/architecture/agents.md) for the owner boundary, access, routing, accounting, current-version cut and examples.

## Status Footer

`status-footer` replaces the TUI footer with one compact line: `Grok 4.6 high (xai sub) | ~/project (main) | <session-uuid> | ↑952k ↓62k R13M CH97.4% $8.979 RB2 31k $0.084 | ✻ 2m10s TTFT 8.1s 25 tok/s | 270k/500k (54.0%) | MCP 2/2`. It is the session lane of the [usage metrics](docs/architecture/usage-metrics.md): every metric is a pure function of the persisted session entries, so a request moves it only when Pi persists that request's assistant message. Subscription status sits in the model parentheses; the branch comes from Pi's footer data and disappears outside a repository; `R`/`W` are cache read/write and `CH` is the session cache-hit rate weighted by prompt tokens across all assistant prompts (the latest request's rate belongs to the working row). `RB` after cost is the session's cumulative cache re-bill count, re-billed tokens and extra dollars, computed exactly as Pi's `/session` "Cache Re-billed" (dollars omitted when the recorded amount is zero, such as on subscriptions); it separates re-bill losses from ordinary new input. `✻ TTFT tok/s` are the session's thinking total, mean time to first token and output tokens per second of request duration, joined read-only from `work-timing` request entries; when those entries are absent only `✻` and `TTFT` are omitted. `$` excludes Pi cache-warming and cache-keepalive usage. When the `fast-gpt` keyed status is present, a warning-colored ⚡ sits after thinking, as in `GPT-5.4 high ⚡ (openai sub)`. Narrow terminals wrap field by field — each field flows onto the next row only when it exceeds the remaining whitespace — adding rows and preserving fields, and truncate a row only when a lone segment cannot fit, preserving the full UUID whenever it fits alone. Identity and traffic use a fixed palette; separators, timing, context/MCP indicators, and lower thinking levels use the active Pi theme. Other extension statuses remain hidden. The extension is inactive in RPC, JSON, and print modes and remains stateless.

## Work Timing

A TUI-only working-row and timing-entry display for one external human interaction, across its model/tool turns, automatic result runs and owned asynchronous waits. `Worked for` settles once the main loop, related executions and pending/reserved result delivery are all quiet; explicit human-only UI wait is excluded, and interrupted or unavailable state receives its corresponding label. The working row is the request lane: the current request's `↓` estimate, `✻` thinking, a running `TTFT…` counter and live `tok/s`, replaced at settlement by that request's `↑ ↓ R W CH $ RB ✻ TTFT tok/s`. The `Worked for` entry is the interaction lane of the same fields, with `✻` shown as a share of work elapsed. `TTFT` and `tok/s` follow OpenRouter's definitions: `tok/s` is output divided by the whole request duration including TTFT, and lane values are ratios of sums. Elapsed time measures wall time independently of parallel child duration sums. The active `⚙` field times the longest-running current tool; tool progress has separate evidence. The main agent judges task completion and continuation; these displays provide timing evidence.

The extension also appends one context-free `work-timing-request` entry per main-session request from its `message_end` handler, before Pi persists the assistant message; it carries the request's `TTFT` and thinking duration, which Pi leaves unpersisted, and the footer joins it read-only.

See [Usage metrics](docs/architecture/usage-metrics.md) for the lane model, field matrix and update cadence, and [Work-timing metrics](docs/architecture/work-timing.md) for request timing, interaction settlement, width behavior and maintenance boundaries. When co-loaded with `pi-cc-extensions`, its competing `enableWorkingMessage` writer must be off; user settings and an already-loaded process retain their existing state after source edits.

## Agent Bark

`agent-bark` sends the optional user-owned `~/.local/bin/agent-bark-hook` one `UserPromptSubmit` when an external interaction starts and one completion when it ends: the moment a person needs to look again. In TUI and RPC it runs its own instance of the shared interaction boundary that also ends `Worked for`, so an intermediate main-run settlement while owned Bash or Agent work still runs, and the internal result-wake runs that follow, stay silent. A quiescent end sends `Stop`; a main-run error or unverifiable execution state sends `StopFailure`, the latter with a `State unavailable:` summary prefix; an abort or new human input stays silent because the person is already present. The payload carries a bounded assistant summary and `duration_ms`, the same main-agent wall time excluding human wait. Print and JSON hosts cannot resume from asynchronous results, so a user run's settlement ends the interaction there. The adapter returns before registering handlers when `PI_EXTENSIONS_AGENT_CHILD=1`, which excludes a managed agent's own Pi process. A missing hook is non-fatal; credentials, thresholds, deduplication, and actual delivery remain the shared hook's responsibility.

When adopting this packaged adapter, disable or remove the old loose `~/.pi/agent/extensions/agent-bark.ts` entry so each main-agent notification is sent once. Loose extensions remain user-owned and unchanged by the package publisher. Removing this package entry stops the Pi adapter and leaves the shared hook and its other consumers unchanged.

## Async Bash

In TUI and RPC, the enhanced `bash` can return while the same native Pi Bash operation keeps running. Pi owns shell selection, launch and process-tree teardown; the wrapper retains output, an execution-scoped abort signal and renewable deadline. Configured cwd, environment and shell command prefix apply once. `inspect` reads the retained result, `wait` can be released while work continues, `renew` extends the same execution, and `cancel` aborts it through Pi. A running result remains distinct from exit 0; the original call returns only once. Print and JSON keep the native draining shell. Notices delivers a terminal result left unreturned by the tool. Start with `{"command":"bun test"}` and control it with `{"action":"inspect","executionId":"exec_example"}`; an execution id requires an explicit action; otherwise the request is rejected before execution. See [Async Bash](docs/architecture/async-bash.md).

## Cache Keepalive

`cache-keepalive` keeps an idle TUI/RPC session's Anthropic prompt cache warm while Pi's own idle warming (still in 1.5.1) stops after a custom message enters the context. It acts only while Pi's global `cacheWarming` setting is explicitly `"streaming"` (Pi's default is `"idle"` since 1.5.1), replays the last real provider payload with a one-token response on Pi's own schedule and economics, and records each refresh as a context-free `cache-keepalive.refresh` entry. Setting `cacheWarming` to `"idle"` returns to the official warmer and makes this extension stand down. See [Cache Keepalive](docs/architecture/cache-keepalive.md).

## Tasklist And Notices

`tasklist` keeps a passive branch-local list with an ordinary title, stable item IDs, text, `todo`, `doing`, `blocked`, `done` or `cancelled` status and optional notes. Use `set`, `update` and `inspect`; `cancel` is a bulk edit of unfinished items; execution cancellation uses its execution's control. List pause/resume, automatic interruption mutation and inferred task completion remain outside Tasklist's behavior. The main agent judges completion and necessary checks; this independent capability works with any Skills collection and leaves update scheduling and turn-ending conditions to the main agent.

Tasklist continues publishing passive facts. Notices alone decides execution-result delivery; task-only notices remain disabled. Unfinished, blocked or cancelled items remain passive while Notices delivers Agent/Bash results, including when a sibling execution is still running. Results supply evidence; the user owns approval and the main agent judges task completion.

`tasks-ui`, `jobs-ui` and `agents-ui` share an above-editor widget with independently expandable Tasks → Jobs → Agents sections. Each heading reads `Name (done/total done) active · alerts`, for example `Tasks · <list title> (3/7 done) 2 doing` or `Jobs (22/24 done) 2 running`, so the line ends on current work. Header clicks fold inline and preserve editor focus; dialogs open through their dedicated commands. Commands accept `expand`, `collapse`, `show`, `hide` and bare visibility toggles; `/xxx-ui list` opens the corresponding read-only central inspector and preserves the bottom section. Updates preserve visibility/folding. Done titles remain struck through. Headless modes keep the tools available and leave the UI unmounted.

Jobs is deliberately Bash-only: it lists background Bash executions; Agents has its separate inspector. `/jobs-ui list` shows the same background commands with pagination; foreground completions are excluded. Rows show bounded command previews and actual execution facts, with running jobs before stopped jobs. The current success-duration threshold is zero. Opening the list preserves inline choices; unavailable data is labeled separately from zero jobs. Agents has its separate inspector.

Tasklist writes schema-v6 snapshots and normalizes the last shipped v5 tracking state in memory, preserving item data and dropping list-control fields. Restoration works immediately and preserves historical entries; the next explicit model edit appends v6. Unsupported state is reported explicitly; an empty list represents supported empty state. Private storage/event names remain compatible. See [Tasklist](docs/architecture/tasklist.md) and [Notices](docs/architecture/notices.md). Source changes still need separately authorized publication and reload before a daily Pi process uses them.
