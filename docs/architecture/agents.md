# Agents

`extensions/agents/index.ts` registers seven tools for named agents in one main session: `invoke_agent`, `message_agent`, `list_agents`, `wait_agents`, `stop_agent`, `release_agent` and `agent_candidate`. The main agent assigns bounded outcomes, tracks overall progress and owns final acceptance with the user. Assignees coordinate work-level matters within their briefs and grants; assigners settle scope, authority and unresolved disputes. Pi owns native model loops and session appends; the extension owns execution, peer transport and retained state. [Notices](notices.md) delivers execution results to the main agent.

[Agent Execution](agent-execution.md) owns the tool, authority, workspace, persistence, candidate and observation contracts. [Execution Primitives](agent-execution-primitives.md) describes the internal Git and supervisor mechanics, and [Agents UI](agents-ui.md) owns display behavior. Portable methods may describe coordination without depending on these tools or role names.

## Assignments, access and workspaces

Invoke one agent with a role, a session-unique `name`, an assignment `prompt` and explicit `access`. Give it the outcome, constraints, checks, peers and what each owns, and say what to send to a peer or return to its assigner. Each `access` rule pairs `permission: "read" | "write"` with an absolute path or a nonempty path list in `scope`; write includes read. One assignment can write several Git repositories and read other Git or non-Git evidence. Admission validates physical identity, containment and supported Git layout; authorization still comes from the user, and a nested invocation stays within the invoking agent's prepared grants for that turn, including their identity pins; an agent working in an isolated copy invokes agents with read access only.

The packaged roles default to a shared workspace. A shared writer changes the granted checkouts directly; review its report alongside the working-tree diff, including new files. Give concurrent writers distinct file and shared-resource ownership: the native tool queue is per process, and overlapping edits can lose updates. `stop_agent` with `revert` restores attributable file-tool changes from the last turn after writer settlement is confirmed, for files physically inside the agent's write grant in the checkout admitted for it, whose contents and mode still match what the agent left and that nobody changed between its writes. Shell changes remain unattributed; review unknown or retained changes in place.

Use `workspace: "isolated"` when integration should be explicit. Each writable Git repository gets pinned input and a private worktree; a successful complete turn with changes produces one candidate bundle. An authorized caller uses `agent_candidate` to apply, refresh or discard by name. Each caller must have been shown the latest result; a stale call shows the new result and leaves the checkout untouched. Applying a candidate, refreshing an idle agent's private input and accepting the business result are separate decisions.

Trusted shell and third-party tools retain host privileges. Native file and typed Git operations enforce declared ranges, including the actual result of an isolated merge; these guards and private worktrees are not an OS sandbox. `git_read` supplies bounded status, diff and history evidence with explicit completeness. Use incomplete or unavailable evidence as such.

## Messages, results and control

Names are addresses used once in a main session, including after release; `main` addresses the main agent, and `assigner` and `peers` are reserved as message selectors. Handles, episodes and candidate IDs are engine correlation data. `message_agent` delivers to a running or starting recipient's next model call after its current tools, or starts exactly one new turn when the recipient is idle; that turn's user input is a neutral host trigger and the messages arrive as agent messages before its first model call. The result belongs to whoever started the turn: a finding sent to a running author leaves the result with the author’s current turn initiator; waking that author with a finding returns the result to the sender. A result receipt to an agent is available in its running turn or held until its next turn; it carries the full report when the initiator is the agent's assigner and the summary otherwise. Messages to the main agent enter as custom messages distinct from user input.

`may` sets messaging to `assigner`, `peers` with the same assigner, or named recipients; it also sets roster visibility and nested invocation. A role supplies defaults unless the invoke call supplies `may`. The assigner and main agent control stop, release, full reports and candidate operations. Peers see summaries when roster visibility allows, and send as their messaging grants allow. An agent message carries the sender's information or direction, never user approval; delivery leaves access unchanged; an agent grants at most what it holds; final acceptance stays with the main agent and the user.

Use `list_agents` for a roster snapshot or a named report; for candidate decisions, a named report or a wait result counts as being shown a result once the caller's next model request carries it, and a roster summary does not. The main agent can read a peer-initiated turn's retained result there without receiving an automatic notice for it. `wait_agents` observes named agents or the running agents the caller invoked; its default budget is 180 seconds. Expiry or early return leaves execution running. Ten minutes without child activity produces one inactivity checkpoint; new activity re-arms it. After interruption or resume, use `list_agents` to recover current work and `stop_agent` to confirm writer settlement before further mutation. The next user-directed turn can carry one bounded recovery hint; ordinary requests keep their stable prefix.

Submission, execution, report completeness, integration, acceptance and resource release are distinct. Verify before accepting, and use `release_agent` after settlement. Retention keeps owned resources available; discard removes owned private working files while preserving registry/native evidence and any already integrated changes. Resolve partial cleanup from retained evidence.

## Roles and routing

The packaged `explorer`, `reviewer` and `worker` definitions express investigation, evaluation and implementation. Define other roles as `NAME.md` under Pi's `agent-roles/` or a trusted project's `.pi/agent-roles/`. For the same name, the trusted project definition takes precedence over the user definition, which takes precedence over the packaged `config/roles/` definition. Frontmatter uses required `name` and `description` and optional `workspace`, `may` and `fallbackRoute`; the Markdown body supplies role instructions. A role sets purpose, workspace and collaboration defaults, while `access` supplies file grants. Packaged roles allow messages to their assigner and peers, show the roster and allow nested invocation.

`config/agent-routes.json` supplies the baseline; Pi's agent-directory `agent-routes.json` is the only user route overlay. Omitted fields inherit the baseline, supplied candidate arrays replace their matching arrays, and invalid or unsafe configuration fails visibly. `routes` is keyed by role name. When a role lacks its own entry, it uses the configured entry named by its `fallbackRoute`, or the invoking main session's model and thinking (`$parent`) if no fallback entry exists. The effective route records that choice as `roleRouteFallback`. `/agents` reports available role definitions, routes, limits and configuration source. The extension reads the files without changing them.

### Profile preferences and model thinking

`executionProfile` selects an ordered list of `{model, thinking}` candidates: `fast` favors quick turnaround, `balanced` weighs cost and quality, and `deep` favors complex work. A fast route may pair a smaller model with high thinking, while a deep route may use a stronger model at medium thinking. Use this preference alone when the configured pair fits the task. An unmapped execution profile uses the role route and records that fallback.

`thinkingProfile` independently requests `light` (low overhead), `standard` (routine reasoning), or `deep` (more deliberation). A configured global thinking-profile mapping overrides the candidate's thinking. Exact `thinking` takes precedence; omitting both keeps the configured value. Exact `model` and `thinking` choices apply only to that invocation and resolve against current host support; an unavailable exact selection fails visibly.

Pi's model metadata owns provider adaptation. For example, a model's `thinkingLevelMap` entry `"medium": "high"` makes Pi's logical `medium` level available and sends the provider's `high` effort. Set aliases in Pi's `models.json` or `modelOverrides`; the route records Pi's logical level. Candidate order selects the first available compatible model at admission. The assigner decides any later reassignment based on the outcome.

## Retained evidence and verification

The current collaboration contract is version 5. Version 4 and older managed records remain untouched and are excluded by current runtime readers; the retired `agent` tool and its request fields have no aliases. One addressable agent binds one native file in its parent project's `sessions/<project>/agents/`, while private registries, provenance and isolated resources live under `managed-agents/`. Native usage can be read independently of runtime discovery; see the [historical usage export](agent-execution.md#historical-usage-export).

Execution observers correlate facts using exact session, turn and candidate identities. They distinguish admission, actual launch, terminal execution and integration. The session hub records [coordination telemetry](agent-execution.md#coordination-telemetry) without message bodies. Multiple repositories or repeated inspection do not multiply recorded native usage or logical candidates; unavailable evidence stays distinct from a successful zero count.

[Offline evidence lanes](../test-suite-evidence-lanes.md) exercise actual host behavior with synthetic input and disposable state; they establish neither live-provider effectiveness nor evidence for unrelated platforms. Source edits, installation, user configuration, and publication keep their own authority and verification.
