# Work-timing metrics

`work-timing` provides TUI timing feedback for one external human interaction: the prompt a person typed or sent, plus every native model run, tool call and idle gap that interaction produces. It owns the working row while a run is in flight and appends one context-free completion entry only when the interaction ends: the main loop is genuinely settled and all work the interaction owns has stopped, including any pending or reserved result delivery, or the main run failed, was interrupted, or its state could not be verified. It does not judge whether the user's task is complete, account for provider billing, or control execution.

The interaction boundary is external input. A native `agent_settled` is an internal run boundary, not the end of the interaction: an automatic result wake that starts another main run remains part of the same span. A run started only by an extension, with no external input behind it, still paints the live row but appends no completion entry.

## Request timing

The working row shows the request lane; the completion entry shows the interaction lane. [Usage metrics](usage-metrics.md) owns the lane field matrix, population, formats and update cadence. Request duration is Pi's assistant `durationMs`, from stream creation before the provider request to response end. Per-request `tok/s` is output divided by request duration in seconds, including first-token wait; aggregates divide eligible output sums by eligible duration sums. This follows [OpenRouter](https://openrouter.ai/docs/guides/best-practices/latency-and-performance) and the multi-turn aggregation of [Artificial Analysis](https://artificialanalysis.ai/methodology/performance-benchmarking).

`TTFT` measures the first observed thinking start or thinking, text or tool-call delta from request start, anchored at message end minus `durationMs`; the live counter starts at the main agent's `before_provider_request`. A transport that never fires that hook, such as an extension provider's custom `streamSimple`, shows neither the live `TTFT…` counter nor live `tok/s`; settled `TTFT` and `tok/s` still come from `durationMs`. Hidden provider reasoning can delay the first observed signal. `✻` is observed thinking duration, not cache-read `R`. The working row may estimate output from streamed characters before settled provider usage replaces it.

## Interaction span and settlement

The span starts when the host reports input from a real external source (interactive or RPC). Extension-origin prompts are automatic continuation: they never start or cut an interaction, and an extension-origin run without an external input keeps the live row only. Queued steering or follow-up input during a streaming run stays inside that run and therefore inside the same interaction. If that run was started by an extension with no human behind it, the external input instead promotes it to a fresh interaction at the input moment: the work-elapsed clock cuts at input, while a request belongs wholly to the interaction in which it settles, and the run's ongoing tool calls and adopted executions stay owned so the work the person is now waiting on is not lost. New external input while an interaction is only awaiting async work cuts the span: the earlier span is reported as `interrupted`, never as a completion, and a late notice from its old jobs cannot reopen it.

The host exposes no identity that pairs an `input` event with the run it starts, and prompt expansion or another handler's transform can change the text, so the binding is ordering-based rather than content-based. It is still exact: every user-message run comes from the host prompt path, which emits `input` first, while custom runs never emit `input`. The most recent input event is therefore the run's input, and every input event replaces or clears the pending start. In particular an extension-origin prompt clears it, so an input that another handler consumed without starting a run cannot let a much later automatic run inherit stale human intent. A handler that replaces human input with its own `sendUserMessage` is the accepted loss of that distinction; no supported correlation hook exists to keep it attached.

The span lifecycle is the shared interaction-boundary algorithm in `extensions/shared/interaction-boundary.ts`. This extension runs its own instance from its own host handlers and keeps only its measurements on the span; Agent Bark runs a separate instance of the same algorithm, so neither reads nor writes the other's state and either works alone.

Settlement is passive and evidence-based. A main run that settles without abort but whose latest assistant message ended with an error closes the span as `failed` at once: Job Notifications stops automatic wakes after an error, so owned jobs cannot resume the loop and a person must look again. Otherwise, after `agent_settled` the extension pulls the shared execution-quiescence snapshot through the notification event bus and appends the summary only when the main loop is idle with no queued message, no in-scope execution is non-terminal, and no in-scope result delivery is pending or reserved for a wake. A settled run whose owned job still executes, or whose terminal result has not yet been delivered, produces no entry; the later delivery wake starts another native run inside the same span, and the single summary is written after that run settles and the same query is quiet. The extension registers no settlement waiter, timer-driven model continuation, widget or command for this; it does not infer completion from task state, assistant prose, elapsed thresholds or job duration.

Only executions attributable to the interaction count. Attribution is the raw `toolCallId` the host gave to any tool call started in the span, including tool calls of automatic result runs, or a producer execution identity explicitly adopted by a control or query receipt the model received (a retained shell `executionId` or an Agent `runId`). Executions already present when the span opens are recorded as excluded, so an older unrelated job neither prolongs the interaction nor becomes its work by accident. A producer that cannot report its facts, or a delivery state blocked for in-scope work, yields `unavailable` rather than a success claim.

Request facts aggregate only the main loop's own requests that settle in the interaction. The interaction's entry population starts at the external input that opened it, so a compaction Pi runs between that input and the run start counts; a promoted run's interaction starts at the promoting input. A parallel child's duration is never added to wall time; child activity only prevents an idle gap from being classified as human wait. The idle gap between runs is part of work elapsed because the person was waiting on autonomous work, not on themselves.

Pure human wait is excluded. While an explicit extension UI prompt is open, elapsed time is attributed to human wait unless a related async execution is progressing; a native tool that is itself blocked on `confirm`, `select` or another prompt is not autonomous progress, so the ordinary in-tool prompt is human wait. If a child or retained Bash job is still working, that interval remains autonomous work. The attribution samples at prompt start and end, at tool boundaries and at observed fact changes, so it is accurate at those boundaries rather than a per-frame reconstruction. Accumulated human wait is stored as `humanWaitMs`, subtracted from `totalMs`, and displayed as `waited <duration>` when it reaches a second.

## Live and settled presentation

The live row shows work elapsed, optional `⚙` active-tool time, then the current request's in-flight `↓` estimate, `✻`, `TTFT x.xs…` live counter and live `tok/s` when available. At `message_end`, settled request values replace estimates and remain while tools run and until the next request starts at `before_provider_request`, or at the first assistant stream event on transports without that stage; `turn_start` alone keeps them, because Pi may still prepare the request. The tool timer tracks the longest-running active tool, excluding extension UI prompts; `+N` counts other active tools. A compound fused call has one tool clock. The native row may stop between runs while the interaction remains open.

The clock refreshes at one-second cadence and stream events update live estimates. Width compaction preserves the head and `⚙` tool field and drops other fields whole. Resize repaints immediately. The completion entry shows its status head, optional `waited`, and interaction-lane metrics, including `✻ <sum> (<share of work elapsed>)`. Durations use compact units such as `1m12s`. Status heads distinguish settled, failed, interrupted and unavailable state; entries fold at field boundaries.

## Persistence, ownership and compatibility

The context-free `work-timing` completion entry is version 5, storing `totalMs`, `humanWaitMs`, `scope`, `status` and interaction aggregate `metrics`. For each main-session request, its `message_end` handler appends a context-free version 1 `work-timing-request` entry with `messageTimestamp`, optional `ttftMs` and `thinkingMs`, before Pi persists the assistant message. Installed Pi 1.5.0 was checked for this ordering. The cutover is forward-only: older-version normalization was removed and historical entries render whatever their stored fields support. Neither entry enters model context.

`work-timing` must remain inactive in headless modes. Final settlement releases its interval and quiescence subscription; session shutdown, session replacement and branch change also release the session-scoped resize listener. A teardown caused by a session or branch boundary writes nothing into the next scope. Disabling/removing the extension stops future timing behavior; it does not rewrite retained session entries or transfer ownership of the working row to another first-party component. `status-footer` owns the footer and `agents-ui` its observer view independently.

When co-loaded with `pi-cc-extensions`, that package's independent `enableWorkingMessage` writer must be off for this extension to own the row without competition. Refresh frequency does not arbitrate writers. Configuration is user-owned: runtime code must not change another extension's settings or patch Pi UI methods to claim the row. Editing this source checkout does not establish what an already-running Pi process or copied installed package loaded.

The [shared usage metrics reference](usage-metrics.md) owns the common definitions. Shared integration guidance lives at `$AGENT_ARCHITECTURE_DIR/docs/architecture/pi-extension-integration.md`; it explains composition, not another implementation or runtime dependency. Different throughput definitions, UI relabeling and execution-observation changes require their own explicit behavior decisions rather than silently changing these counters.
